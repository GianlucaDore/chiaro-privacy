## 1. Il problema

### 1.1 Che cosa non funziona senza

Oggi, per far girare Chiaro su una macchina nuova, servono: Python 3.12 (non 3.11, non 3.13),
`pipenv`, Node in una versione abbastanza recente, `npm install`, due terminali aperti, e la
conoscenza di quali comandi lanciare in quale cartella. Sono le istruzioni del README, e sono
sei righe che funzionano **finché la macchina somiglia alla tua**.

Il problema non è la fatica: è che quelle sei righe **non sono verificabili**. Nessuno sa se
funzionano su una macchina pulita, perché nessuno ha una macchina pulita. Quando il tuo
portatile ha già Python 3.12 installato, il README che dice «installa Python 3.12» è una
dichiarazione di fede.

> Un progetto che si avvia solo dove è stato scritto non è un progetto avviabile: è un
> progetto che funziona per una persona sola.

### 1.2 Che cosa ci guadagni

Con i due Dockerfile e il compose, l'istruzione per avviare Chiaro diventa una:

```bash
docker compose up
```

Non serve Python, non serve Node, non serve sapere cosa sia `pipenv`. Serve Docker. È anche
la ragione per cui questo passo sta nella fase 0 e non alla fine: chi guarda il progetto per
valutarti lo prova, e se provarlo costa mezz'ora di installazioni non lo prova.

## 2. Il meccanismo

### 2.1 Immagine, container, Dockerfile

Tre parole che si confondono, e conviene fissarle subito.

**L'immagine** è un filesystem congelato: una cartella con dentro un sistema operativo minimo,
l'interprete, le librerie e il tuo codice. È **immutabile** e non sta girando. Pensa a un file
`.iso`.

**Il container** è un'immagine **in esecuzione**. Si crea, gira, si ferma, si butta. Quando lo
butti, tutto ciò che ha scritto sul proprio filesystem sparisce — e questo è il punto che si
dimentica più spesso, perché è il motivo per cui i database nei container hanno bisogno dei
*volumi*.

**Il Dockerfile** è la ricetta: la sequenza di istruzioni che, eseguite, producono l'immagine.

> Il Dockerfile sta all'immagine come il codice sorgente sta all'eseguibile, e il container
> sta all'immagine come il processo sta all'eseguibile.

### 2.2 I layer, e perché l'ordine delle istruzioni conta

È il concetto centrale del passo, ed è anche quello su cui il criterio ti interroga.

**Ogni istruzione del Dockerfile produce un layer**: una fotografia delle differenze che quella
istruzione ha prodotto sul filesystem rispetto al layer precedente. L'immagine finale è la pila
di tutti i layer, sovrapposti in ordine.

Quando ricostruisci, Docker percorre le istruzioni dall'alto e per ognuna si chiede: *l'ho già
eseguita, con esattamente questo input, partendo da esattamente lo stesso layer di prima?* Se
sì, non la riesegue: riusa il layer che ha in cache. **Al primo «no», la cache si rompe, e da lì
in giù tutto viene rieseguito** — anche le istruzioni che non sono cambiate, perché il layer da
cui partono è nuovo.

Questa è la regola che decide l'ordine delle istruzioni:

> Le cose che cambiano di rado stanno in alto. Le cose che cambiano a ogni salvataggio stanno
> in basso.

Il tuo codice applicativo cambia venti volte al giorno. Le dipendenze cambiano una volta al
mese. Quindi:

```dockerfile
# ❌ SBAGLIATO: il codice entra prima delle dipendenze
COPY . .
RUN pip install -r requirements.txt
```

Qui `COPY . .` copia anche `main.py`. Cambi una riga di `main.py`, quel layer cambia, e il
`RUN pip install` sottostante viene rieseguito da zero: **reinstalli tutte le dipendenze
perché hai corretto un refuso.**

```dockerfile
# ✅ GIUSTO: prima il manifesto delle dipendenze, poi l'installazione, poi il codice
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
```

Ora cambiare `main.py` invalida solo l'ultimo layer. L'installazione delle dipendenze è sopra,
il suo input (`requirements.txt`) non è cambiato, e Docker la salta.

**È esattamente ciò che il criterio di questo passo ti chiede di dimostrare.**

### 2.3 La build multi-stage, e perché serve al frontend

Il frontend ha una caratteristica che il backend non ha: **gli strumenti che servono per
costruirlo non servono per eseguirlo.**

Per costruire il frontend servono Node, npm, TypeScript, Vite, ESLint, 315 pacchetti in
`node_modules`. Il risultato di quella costruzione sono pochi file statici in `dist/`: un HTML,
un JS, un CSS. Per **servirli** non serve Node: serve un server web che restituisca file, e il
mestiere di nginx è esattamente quello.

Se costruisci e servi nella stessa immagine, spedisci un'immagine da quasi un gigabyte che
contiene il compilatore TypeScript, il motore di test e mezzo registro npm — tutta roba che non
verrà mai eseguita, e ognuna delle quali è superficie d'attacco.

La build multi-stage risolve così: **più blocchi `FROM` nello stesso Dockerfile.** Ogni `FROM`
apre uno stadio nuovo. Alla fine, l'immagine prodotta è **solo l'ultimo stadio**; gli stadi
precedenti vengono scartati. L'istruzione `COPY --from=<stadio>` è il ponte che permette
all'ultimo di prendere qualcosa da uno dei precedenti.

```dockerfile
FROM node:24-alpine AS costruzione
# ... qui si compila, e questo stadio pesa centinaia di MB

FROM nginx:alpine
COPY --from=costruzione /app/dist /usr/share/nginx/html
# l'immagine finale contiene nginx e pochi file statici. Niente Node.
```

Il backend non ne ha bisogno: Python è interpretato, e l'interprete che serve a installare le
dipendenze è lo stesso che serve a eseguire l'applicazione.

### 2.4 `CMD` contro `ENTRYPOINT`

Entrambe dicono cosa eseguire all'avvio del container. La differenza è **cosa succede se chi
avvia il container scrive un comando dopo il nome dell'immagine.**

- **`CMD`** è un *default sostituibile*. `docker run immagine bash` **sostituisce** il `CMD`
  con `bash`.
- **`ENTRYPOINT`** è *fisso*. `docker run immagine --workers 8` non lo sostituisce: gli
  **aggiunge** `--workers 8` come argomenti.

La regola pratica:

> Usa `CMD` quando l'immagine è un ambiente in cui il comando di default è solo il caso più
> comune. Usa `ENTRYPOINT` quando l'immagine **è** un comando, e vuoi che chi la avvia possa
> soltanto passargli opzioni.

Un'ultima cosa che vale per entrambe: esistono in due forme.

```dockerfile
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0"]   # ✅ forma exec
CMD uvicorn app.main:app --host 0.0.0.0                # ❌ forma shell
```

La forma shell avvia in realtà `/bin/sh -c "uvicorn ..."`, quindi il processo numero 1 del
container è la shell e uvicorn è suo figlio. **I segnali arrivano al processo 1**: quando fai
`docker compose down`, Docker manda `SIGTERM`, la shell lo riceve e non lo gira a nessuno,
uvicorn non sa che deve spegnersi, e dopo dieci secondi di attesa Docker lo ammazza. Con la
forma exec, uvicorn *è* il processo 1 e riceve il segnale.

### 2.5 Perché non si gira come root

Dentro un container si è **root per default**, e l'illusione è che non abbia importanza perché
«tanto è isolato».

Ha importanza per due ragioni. La prima: se qualcuno riesce a eseguire codice attraverso la tua
applicazione, lo esegue come root **dentro** il container — può installare programmi, leggere
qualunque file, modificare l'applicazione stessa. Un utente non privilegiato non può fare
niente di tutto questo. La seconda: `root` dentro il container, in una configurazione Docker
classica, è **lo stesso UID 0 del kernel della macchina ospite**. L'isolamento è ottenuto con i
namespace, non con un'identità diversa, e ogni fuga dal container parte da lì.

La creazione dell'utente si fa **prima** di `USER`, e da quel punto in poi ogni istruzione — e
il processo del container — gira con quell'identità. Attenzione all'ordine: dopo `USER` non
puoi più scrivere in cartelle che appartengono a root.

### 2.6 `.dockerignore`

Prima di eseguire una qualunque istruzione, Docker impacchetta la cartella che gli hai indicato
— il **contesto di build** — e la spedisce al demone. Tutta. Compresi `node_modules`, `.venv`,
`.git`, `coverage/`, `.ruff_cache`.

Su questo progetto è quasi mezzo gigabyte spedito a ogni build per essere poi ignorato. Ma il
costo peggiore non è il tempo:

- **`COPY . .` copia anche ciò che non volevi**: un `.env` con delle chiavi finisce dentro
  l'immagine, e le immagini si pubblicano;
- **`node_modules` copiato dall'ospite rompe la build**: contiene binari compilati per Windows,
  e il container è Linux;
- **la cache si rompe in continuazione**: se il contesto include `.git`, ogni commit cambia il
  contesto, e ogni `COPY . .` produce un layer nuovo anche quando il codice è identico.

`.dockerignore` sta **nella cartella del contesto di build** e ha la stessa sintassi di
`.gitignore`. ❗ Docker **non legge `.gitignore`**: sono due file distinti, e dimenticare il
secondo è l'errore più comune di tutti.

### 2.7 Riferimento: ogni istruzione, con la sua forma

Questa sezione esiste perché il resto del briefing spiega il **perché** e non serve a niente
se non si sa il **come**. Ogni riga qui sotto è la forma dell'istruzione più un esempio
completo, e gli esempi sono **volutamente su un progetto diverso dal nostro**: servono a
mostrare come si scrive, non a darti la risposta.

L'applicazione degli esempi è un ipotetico servizio Ruby che sta in `server.rb` e legge le
proprie dipendenze da un file `Gemfile`.

```dockerfile
FROM <immagine>:<etichetta>
FROM <immagine>:<etichetta> AS <nome dello stadio>

FROM ruby:3.4-slim
FROM ruby:3.4-slim AS costruzione
```

```dockerfile
ENV <CHIAVE>=<valore>
ENV <CHIAVE>=<valore> <ALTRA_CHIAVE>=<valore>

ENV RUBY_YJIT_ENABLE=1
ENV LANG=C.UTF-8 TZ=Europe/Rome
```

Una sola `ENV` può impostare più variabili, ed è preferibile: ogni istruzione è un layer.

```dockerfile
WORKDIR <percorso assoluto dentro l'immagine>

WORKDIR /srv
```

Da qui in poi ogni percorso relativo parte da `/srv`. Se la cartella non esiste viene creata.

```dockerfile
RUN <comando da eseguire durante la costruzione>
RUN <comando> \
 && <altro comando>

RUN gem install bundler
RUN apt-get update \
 && apt-get install -y --no-install-recommends libpq-dev \
 && rm -rf /var/lib/apt/lists/*
```

Il comando è quello che scriveresti in un terminale Linux. La forma con `\` e `&&` unisce più
comandi in **un solo layer**, ed è il modo in cui si evita che una cache scaricata resti a
pesare nell'immagine per sempre.

```dockerfile
COPY <origine nel contesto di build> <destinazione nell'immagine>
COPY <origine1> <origine2> <cartella di destinazione>/

COPY Gemfile Gemfile.lock ./
COPY lib/ ./lib/
COPY . .
```

⚠️ Con più origini, la destinazione **deve** finire con `/`. Il `./` significa «la cartella di
lavoro corrente», cioè quella dichiarata con `WORKDIR`.

```dockerfile
RUN useradd --create-home <nome utente>
RUN chown -R <nome utente> <percorso>
USER <nome utente>

RUN useradd --create-home app && chown -R app /srv
USER app
```

Sono due cose distinte: `useradd` è un normale comando Linux eseguito da `RUN`, e crea
l'utente dentro l'immagine; `USER` è un'istruzione di Docker, e dice che da quel punto in poi
si cambia identità. `chown` assegna la proprietà di una cartella, e serve se l'applicazione
ci deve scrivere.

```dockerfile
EXPOSE <porta>

EXPOSE 3000
```

```dockerfile
CMD ["<eseguibile>", "<argomento>", "<argomento>"]
ENTRYPOINT ["<eseguibile>", "<argomento>"]

CMD ["ruby", "server.rb", "--bind", "0.0.0.0"]
```

Ogni parola separata da uno spazio nel comando diventa **un elemento distinto della lista**,
virgolette comprese. Un argomento e il suo valore sono due elementi, non uno:
`"--bind", "0.0.0.0"` e non `"--bind 0.0.0.0"`.

```dockerfile
COPY --from=<nome dello stadio> <origine> <destinazione>

COPY --from=costruzione /srv/public ./public
```

## 3. Gli errori tipici

Sono sette, e i primi due sono specifici di *questo* progetto: li sbaglieresti anche sapendo
tutto di Docker.

### 3.1 ❗ Il Pipfile deve restare dentro l'immagine

Guarda `backend/app/core/config.py`:

```python
MARCATORE_RADICE = "Pipfile"

def get_backend_root() -> Path:
    return risali_fino_al_marcatore(Path(__file__).resolve().parent)

DOTENV = get_backend_root() / ".env"
```

L'applicazione trova la propria radice **cercando il Pipfile**, e lo fa al momento
dell'importazione del modulo, non all'avvio. L'istinto in Docker è di copiare il manifesto
delle dipendenze, installarle e poi liberarsene per tenere l'immagine snella: qui quell'istinto
produce un container che **non importa nemmeno**, con un `RuntimeError: Radice del backend non
trovata`.

⚠️ Non è un difetto da aggirare nel Dockerfile. È un vincolo dell'applicazione, e il Dockerfile
deve rispettarlo: il `Pipfile` resta accanto ad `app/`.

### 3.2 ❗ `--host 127.0.0.1` rende il backend irraggiungibile

Gli script del `Pipfile` dicono così:

```
dev  = "uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload"
prod = "uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 4"
```

`127.0.0.1` significa «accetta connessioni solo da questa macchina», ed è la scelta giusta in
locale. Dentro un container, «questa macchina» **è il container**: la pubblicazione della porta
inoltra il traffico all'interfaccia di rete del container, che non è il suo loopback. Il
risultato è un container che parte, dice «Uvicorn running», e a cui non risponde nessuno —
dall'esterno la connessione viene rifiutata.

Dentro il container serve `--host 0.0.0.0`, cioè «tutte le interfacce».

⚠️ Da cui segue che **il `CMD` del Dockerfile non può essere `pipenv run prod`**: quello script
ha l'host sbagliato.

### 3.3 Alpine va bene per Node, è una trappola per Python

Le immagini `-alpine` sono piccole perché usano **musl** come libreria C al posto di **glibc**.

Per Node non cambia nulla: il tuo codice è JavaScript, e i pochi pacchetti con parti native
hanno binari musl pronti.

Per Python è un'altra storia. I pacchetti Python distribuiscono binari precompilati (le
*wheel*) costruiti per glibc. Su Alpine quelle wheel non sono compatibili, quindi `pip` **ricade
sulla compilazione dal sorgente**: la build passa da un minuto a dieci, servono compilatore e
header di sviluppo, e l'immagine finisce per essere più grande di quella da cui volevi
scappare.

> Per Python si usa `-slim`, che è Debian con glibc e senza il superfluo.

### 3.4 `npm install` al posto di `npm ci`

`npm install` può **modificare** il lock file per soddisfare i range di `package.json`. In una
build questo significa che l'immagine di oggi e quella di domani possono contenere versioni
diverse a parità di codice sorgente.

`npm ci` cancella `node_modules`, installa **esattamente** ciò che dice `package-lock.json` e
fallisce se il lock non è coerente con `package.json`. È il comando delle build automatiche.

⚠️ E non aggiungere `--omit=dev`: la build ha bisogno di TypeScript e Vite, che stanno in
`devDependencies`. La distinzione fra dipendenze di sviluppo e di produzione ha senso per il
backend, dove il processo che gira importa i pacchetti; per il frontend le dipendenze servono
**tutte** allo stadio di costruzione e **nessuna** a quello finale.

### 3.5 Il router del frontend e il 404 all'aggiornamento della pagina

Il frontend usa `BrowserRouter`. Quando navighi da dentro l'app verso `/analisi`, l'URL cambia
ma **nessuna richiesta parte**: è React a cambiare cosa disegna. Se invece premi F5 su
`/analisi`, il browser chiede davvero quel percorso a nginx, che cerca un file chiamato
`analisi`, non lo trova, e risponde 404.

La cura è dire a nginx: *se non trovi il file, servi `index.html`*. Il file `nginx.conf` è già
scritto e lo fa; serve saperlo perché è una domanda da colloquio frequente, e perché è il modo
in cui si scopre che una SPA e un sito statico non si servono allo stesso modo.

### 3.6 Il container non ha memoria

Il backend crea `uploads/` all'avvio, e più avanti ci sarà un file SQLite. Tutto ciò che viene
scritto dentro il container **sparisce quando il container viene ricreato** — non quando viene
fermato e riavviato, ma quando viene sostituito da uno nuovo, cioè a ogni
`docker compose up --build`.

La soluzione sono i **volumi**: una cartella che vive fuori dal container e viene innestata
dentro. Nel `docker-compose.yml` che ti lascio ce n'è uno per `uploads/`, e la ragione è
commentata lì.

### 3.7 `EXPOSE` non pubblica niente

`EXPOSE 8000` è **documentazione**. Dichiara che l'immagine si aspetta di essere contattata su
quella porta, e non apre nulla. La pubblicazione verso l'esterno la fa `ports:` nel compose (o
`-p` in `docker run`). Scrivere `EXPOSE` e aspettarsi che basti è un classico.

### Ordine consigliato

Fai **prima il backend** e verificalo da solo, poi il frontend. Due immagini rotte insieme sono
molto più difficili da diagnosticare di una alla volta.

```bash
# il backend, da solo
docker compose up --build backend
curl http://localhost:8000/docs

# il frontend, da solo
docker compose up --build frontend
curl http://localhost:8081/
```

Se un container parte e muore subito, `docker compose logs backend` è la prima cosa da
guardare: il messaggio c'è quasi sempre, e quasi sempre è uno dei sette errori della sezione 3.

## 5. Il criterio

Ha **due metà**, e la seconda è quella che dimostra di aver capito.

### Prima metà: da clone pulito, l'app si avvia

```bash
docker compose up --build
```

e poi, con gli occhi: `http://localhost:8081` mostra il layout dell'app, e
`http://localhost:8000/docs` mostra Swagger.

### Seconda metà: la prova della cache

```bash
# 1. costruisci una volta
docker compose build

# 2. cambia UNA riga di codice applicativo (non le dipendenze):
#    per esempio il titolo in frontend/index.html, o un commento in app/main.py

# 3. ricostruisci e leggi l'output
docker compose build
```

✅ **Quello che devi vedere**: le righe dell'installazione delle dipendenze marcate `CACHED`, e
solo i layer dal `COPY` del codice in giù rieseguiti.

❌ **Se vedi `pipenv install` o `npm ci` rieseguirsi**, l'ordine delle istruzioni è sbagliato:
qualcosa che cambia spesso sta sopra qualcosa che cambia di rado.

Il secondo strumento di verifica è `docker history`, che elenca i layer di un'immagine con la
loro dimensione:

```bash
docker history chiaro-backend
docker history chiaro-frontend
docker images | grep chiaro
```

Sul frontend serve anche a misurare il guadagno della multi-stage. Un'immagine frontend
**sopra i 100 MB** è il segnale che qualcosa dello stadio di costruzione è finito in quello
finale.

### Tre scostamenti dal briefing

- **Il frontend esce sulla porta 8081, non sulla 8080.** Sulla macchina di sviluppo la 8080 è
  occupata da un altro progetto; con la porta è stato allineato anche `BACKEND_CORS_ORIGIN`,
  che senza quella modifica avrebbe bloccato le chiamate del browser al backend.
- **`uploads/` viene creata nell'immagine**, non lasciata all'applicazione. Il compose ci monta
  sopra un volume prima che il processo parta, e un punto di innesto che nell'immagine non esiste
  nasce di root: il container partiva e rispondeva, ma alla prima scrittura avrebbe dato
  `Permission denied`. Il guasto non emergeva né dalla build né dall'healthcheck.
- **Nel frontend `COPY . .` è la scelta giusta**, al contrario del backend: `tsc -b` legge
  tsconfig che dichiarano anche `tests/**` e `vitest.config.ts`.
