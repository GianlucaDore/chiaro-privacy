# 0.6 — Migrazione a React 19

🟡 **Zona gialla: il codice lo scrivi tu.** Io spiego e poi ti interrogo.

> Questo briefing è scritto per chi conosce **React 18 e basta**. Per ogni cosa che cambia
> trovi come si scriveva prima, come si scrive adesso, e perché è cambiato. Niente è dato
> per scontato: se un termine compare, prima viene spiegato.

I cartelli `TODO(0.6/n)` sono in `frontend/src/main.tsx`, `frontend/src/theme/index.ts` e
`frontend/vite.config.ts`.

---

## 1. Perché questo passo esiste

Non è un aggiornamento di cortesia, ed è importante capirlo prima di iniziare.

Il `CLAUDE.md` di questo progetto **vieta** Redux, TanStack Query e qualunque altra libreria
di data fetching. Quel divieto poggia su una frase precisa: *«`use()` e `useOptimistic`
coprono le operazioni principali»*. Quelle due funzioni **su React 18 non esistono**. Lo
stesso vale per il divieto di scrivere `useMemo` e `useCallback` a mano, che si regge sul
React Compiler.

Finché il progetto resta su React 18, tre decisioni di architettura già prese non hanno le
fondamenta sotto.

> Questo passo non aggiunge funzionalità: rende possibili quelle che verranno.

## 2. La mappa: tre categorie, non una

Quando si legge «migrazione a React 19» si pensa a una lista di cose rotte. In realtà i
cambiamenti stanno in tre categorie molto diverse fra loro, e confonderle è il modo più
rapido per perdersi.

| **_Categoria_** | **_Cosa contiene_** | **_Ti riguarda oggi?_** |
| --- | --- | --- |
| **Le rimozioni** | API deprecate da anni, adesso sparite | Sì, ma questo codice non ne usa nessuna |
| **Le semplificazioni** | Cose che si facevano in due passaggi e ora se ne fanno in uno | Sì, cambiano come scriverai da qui in poi |
| **Le novità** | `use()`, le Action, `useOptimistic`, i metadata | Non oggi, ma sono il motivo del passo |

Le sezioni 3, 4 e 5 seguono queste tre categorie nell'ordine.

## 3. Le rimozioni
---

Sono le API che React deprecava da anni con un warning in console e che in 19 non esistono
più. Il codice che le usa non stampa un avviso: **si rompe**.

### 3.1 `ReactDOM.render` non c'è più

È la rimozione più grossa, e vale la pena capirla perché spiega tutte le altre.

❌ Come si scriveva fino a React 17:

```tsx
import ReactDOM from 'react-dom';

ReactDOM.render(<App />, document.getElementById('root'));
```

✅ Come si scrive da React 18 in poi:

```tsx
import { createRoot } from 'react-dom/client';

createRoot(document.getElementById('root')!).render(<App />);
```

React 18 aveva introdotto `createRoot` **affiancandolo** al vecchio `render`, che continuava
a funzionare stampando un warning. React 19 ha tolto il vecchio.

Il motivo non è estetico. `createRoot` crea una **radice concorrente**: una radice che può
interrompere un rendering a metà, metterlo da parte e riprenderlo dopo, per dare la
precedenza a qualcosa di più urgente — tipicamente la reazione a un click. Tutto ciò che
React 18 ha introdotto (`useTransition`, `useDeferredValue`, `Suspense` per i dati) funziona
solo dentro una radice concorrente. Tenere in vita il vecchio `render` significava tenere in
piedi due motori di rendering diversi.

> Chi passa da 17 a 19 in un colpo solo trova qui il muro. Noi no: `main.tsx` usa già `createRoot`.

Insieme a `render` sono spariti i suoi compagni:

- `ReactDOM.hydrate` → si usa `hydrateRoot` (serve solo col server-side rendering, che qui non c'è)
- `unmountComponentAtNode` → si usa `root.unmount()`
- `ReactDOM.findDOMNode` → si usa un `ref`

### 3.2 `propTypes` e `defaultProps` sui componenti funzione

Prima che TypeScript diventasse la norma, il modo di dichiarare che tipo avessero le props
era una proprietà attaccata alla funzione.

❌ Il vecchio modo:

```tsx
function Saluto({ nome, urlante }) {
  return <p>{urlante ? nome.toUpperCase() : nome}</p>;
}

Saluto.propTypes = { nome: PropTypes.string.isRequired };
Saluto.defaultProps = { urlante: false };
```

✅ Il modo di adesso, con TypeScript e i default nei parametri:

```tsx
type Props = { nome: string; urlante?: boolean };

function Saluto({ nome, urlante = false }: Props) {
  return <p>{urlante ? nome.toUpperCase() : nome}</p>;
}
```

React 19 ignora `propTypes` e non applica più `defaultProps` sui componenti **funzione**.
Attenzione a quest'ultimo punto: se il codice si affidava a `defaultProps`, la prop arriva
`undefined` e **nessuno avvisa**. È un guasto silenzioso, non un errore.

Sui componenti **classe** `defaultProps` continua a funzionare, perché lì la sintassi dei
default nei parametri non esiste.

### 3.3 ❗ La trappola: i `defaultProps` che non sono quelli

In `src/theme/index.ts` di questo progetto ci sono tre `defaultProps`:

```ts
MuiButton: {
  defaultProps: { variant: 'contained', size: 'medium' },
  ...
}
```

Si chiamano come l'API appena rimossa e **non c'entrano niente**. Quella è una chiave del
**tema di MUI**: una tabella di configurazione che dice a MUI «quando qualcuno usa
`<Button>` senza specificare `variant`, passagli `contained`». Non è una proprietà attaccata
a una funzione componente, è un dato dentro un oggetto che MUI legge a runtime.

> Le due cose condividono il nome e nient'altro. Cancellare quelle righe romperebbe il tema, e React non c'entrerebbe nulla.

Questa è la domanda 2 delle verifiche.

### 3.4 I `ref` come stringa

❌ Sintassi del 2015, rimossa:

```tsx
<input ref="campoNome" />
// e poi, dentro la classe: this.refs.campoNome
```

✅ Oggi:

```tsx
const campoNome = useRef<HTMLInputElement>(null);

<input ref={campoNome} />
```

Era rimasta viva solo nelle classi molto vecchie. Non la incontrerai qui.

### 3.5 `act` ha cambiato casa

`act` è la funzione che nei test dice a React «esegui adesso tutti gli aggiornamenti in
sospeso, prima che io controlli il risultato». Serve perché React raggruppa gli aggiornamenti
e li applica in modo asincrono: senza `act`, un test ispeziona il DOM prima che React lo
abbia toccato.

- ❌ Prima: `import { act } from 'react-dom/test-utils';`
- ✅ Adesso: `import { act } from 'react';`

Tutto il resto di `react-dom/test-utils` è stato rimosso. Ci tornerai al passo **0.8**, quando
arriveranno Vitest e React Testing Library — e lì i tuoi appunti su RTL sono già pronti.

### 3.6 Le altre, in breve

Spariti anche il **context legacy** (`contextTypes` e `getChildContext`, la sintassi
precedente a `createContext`), `React.createFactory`, e i *module pattern factory*, cioè i
componenti che invece di JSX ritornavano un oggetto con dentro un metodo `render`. Se non
dicono niente, è perché appartengono a un React che non hai mai usato.

## 4. Le semplificazioni
---

Qui non si rompe niente: cambia il modo in cui si scrive. Sono le quattro cose che ti
cambieranno le abitudini.

### 4.1 `ref` è diventato una prop normale

È il cambiamento che si nota di più nell'uso quotidiano.

**Il problema che c'era.** In React 18, `ref` e `key` non erano props come le altre: React le
intercettava e le toglieva dall'oggetto `props` prima di consegnarlo alla funzione. Un
componente funzione quindi **non poteva riceverle**. Scrivendo:

```tsx
function Campo(props) {
  return <input {...props} />;
}

<Campo ref={mioRef} />   // React 18: warning, e mioRef.current resta null
```

il `ref` non arrivava mai all'`<input>`. Per farcelo arrivare serviva un involucro.

❌ React 18:

```tsx
import { forwardRef } from 'react';

const Campo = forwardRef<HTMLInputElement, Props>((props, ref) => {
  return <input ref={ref} {...props} />;
});
```

Nota la forma: la funzione riceve **due argomenti** invece di uno, proprio perché il `ref` non
poteva viaggiare dentro il primo.

✅ React 19:

```tsx
type Props = { ref?: React.Ref<HTMLInputElement>; segnaposto?: string };

function Campo({ ref, segnaposto }: Props) {
  return <input ref={ref} placeholder={segnaposto} />;
}
```

`ref` viaggia dentro `props` come qualsiasi altra cosa, e la funzione torna ad avere un solo
argomento.

> `forwardRef` continua a funzionare, ma è deprecato: da qui in poi è un involucro senza più lavoro da fare.

`key` invece **resta speciale**: React la usa per riconoscere gli elementi di una lista fra un
rendering e l'altro, quindi le serve prima di costruire il componente, e non la passa.

### 4.2 `<Context>` al posto di `<Context.Provider>`

❌ React 18:

```tsx
const TemaContext = createContext('chiaro');

<TemaContext.Provider value="scuro">
  <App />
</TemaContext.Provider>
```

✅ React 19:

```tsx
<TemaContext value="scuro">
  <App />
</TemaContext>
```

L'oggetto ritornato da `createContext` **è** il provider. La vecchia forma funziona ancora ma
verrà rimossa.

### 4.3 `useRef` vuole sempre un argomento

- ❌ `const riferimento = useRef();` — adesso è un errore di tipo.
- ✅ `const riferimento = useRef<HTMLInputElement>(null);`

Il motivo è che `useRef()` nudo era ambiguo: TypeScript non poteva sapere se `current`
sarebbe stato leggibile, scrivibile, o `undefined` per sempre. Obbligare a passare il valore
iniziale toglie l'ambiguità.

### 4.4 ⚠️ I ref callback e la funzione di pulizia

Questa è la trappola vera di React 19, perché **il codice sembra identico e si comporta
diversamente**.

Un *ref callback* è un `ref` a cui passi una funzione invece di un oggetto: React te la chiama
con l'elemento del DOM quando lo monta, e con `null` quando lo smonta.

In React 18 il valore che quella funzione ritornava veniva ignorato, quindi questo andava
bene:

```tsx
let campo;

<input ref={el => (campo = el)} />
```

Una freccia senza graffe ritorna implicitamente il risultato dell'espressione — qui
l'elemento appena assegnato. React 18 lo buttava via.

React 19 ha aggiunto la possibilità di ritornare una **funzione di pulizia**, esattamente come
fa `useEffect`:

```tsx
<input
  ref={el => {
    const osservatore = new ResizeObserver(() => { /* ... */ });
    osservatore.observe(el);
    return () => osservatore.disconnect();   // <- la pulizia
  }}
/>
```

Il che significa che **il valore ritornato adesso conta**. Una freccia con ritorno implicito
sta consegnando a React un elemento del DOM al posto di una funzione.

- ❌ `ref={el => (campo = el)}` — rotto
- ✅ `ref={el => { campo = el; }}` — corretto: le graffe rendono la funzione senza ritorno

> Se React 19 dà un errore di tipo su un `ref`, nove volte su dieci mancano le graffe.

Questa è la domanda 5 delle verifiche.

### 4.5 Gli errori di idratazione diventano leggibili

Minore, ma piacevole: quando il DOM generato dal server non combacia con quello generato dal
client, React 19 mostra la **differenza fra i due** invece dei cinque warning generici di
prima. Qui non c'è server-side rendering, quindi non lo vedrai.

## 5. Le novità — perché siamo venuti fin qui
---

Non si usano in questo passo. Si spiegano adesso perché sono la risposta alla domanda «perché
non posso restare su 18?».

### 5.1 `use()` — leggere una promise dentro il componente

In React 18, per mostrare dati che arrivano da un `fetch`, servivano uno stato, un effetto e
tre casi da gestire.

❌ React 18:

```tsx
function Analisi({ id }) {
  const [dati, setDati] = useState(null);
  const [errore, setErrore] = useState(null);

  useEffect(() => {
    fetch(`/api/analisi/${id}`)
      .then(r => r.json())
      .then(setDati)
      .catch(setErrore);
  }, [id]);

  if (errore) return <p>Errore</p>;
  if (!dati) return <p>Caricamento…</p>;
  return <Rilievi dati={dati} />;
}
```

✅ React 19:

```tsx
function Analisi({ promessa }: { promessa: Promise<Dati> }) {
  const dati = use(promessa);       // si ferma qui finché la promise non si risolve
  return <Rilievi dati={dati} />;
}
```

Il caricamento lo gestisce un `<Suspense>` attorno al componente, l'errore un
`<ErrorBoundary>`. I tre casi non stanno più dentro la funzione.

`use` non è un hook nel senso stretto: **può essere chiamato dentro un `if` e dentro un
ciclo**, cosa vietata a tutti gli altri. Questa singola funzione è il motivo per cui il
progetto può permettersi di rifiutare TanStack Query.

### 5.2 Le Action e `useActionState`

Una *Action* è una funzione asincrona passata direttamente a un `<form>`. React ne gestisce lo
stato di invio, l'errore e il reset.

```tsx
const [errore, invia, inCorso] = useActionState(
  async (statoPrecedente, datiDelForm: FormData) => {
    const esito = await registra(datiDelForm);
    return esito.errore ?? null;
  },
  null,
);

<form action={invia}>
  <input name="email" />
  <button disabled={inCorso}>Registrati</button>
</form>
```

`inCorso` è il flag «sto inviando» che in React 18 tenevi a mano in un `useState`. Serviranno
dalla fase 2, quella dell'autenticazione.

### 5.3 `useOptimistic`

Mostra subito il risultato che *ti aspetti*, poi lo corregge se il server dice altro. È quello
che fa una chat quando il messaggio appare prima di essere partito davvero. In React 18 lo si
scriveva a mano tenendo due copie dello stato.

### 5.4 I metadata si sollevano da soli

Un `<title>` o un `<meta>` scritto dentro un componente, a qualunque profondità, viene spostato
da React dentro l'`<head>` del documento. Prima serviva una libreria apposita.

## 6. Il React Compiler
---

Va capito adesso perché il `CLAUDE.md` **lo dà già per attivo** quando vieta `useMemo` e
`useCallback` scritti a mano.

**Il problema che risolve.** In React, quando un componente si ri-renderizza, tutto ciò che sta
nel suo corpo viene ricalcolato: gli oggetti, gli array, le funzioni. Un array ricreato è un
oggetto nuovo, quindi i figli che lo ricevono come prop lo vedono cambiato anche se il
contenuto è identico, e si ri-renderizzano a loro volta. La cura, fino a ieri, era avvolgere a
mano ogni valore:

```tsx
const filtrati = useMemo(() => rilievi.filter(r => r.grave), [rilievi]);
const apri = useCallback(() => setAperto(true), []);
```

È un lavoro meccanico, facile da dimenticare e facile da sbagliare — un array di dipendenze
incompleto produce un bug che si manifesta molto lontano da dove è stato scritto.

**Cos'è il compilatore.** Un programma che gira **al momento del build**, non nel browser:
legge i componenti, ricostruisce da solo quali valori dipendono da cosa, e inserisce lui la
memoizzazione. Il risultato è che scrivi il codice semplice e ottieni quello ottimizzato.

> Il React Compiler non fa parte di React 19: è un plugin Babel separato, da installare e configurare.

Tecnicamente è il pacchetto `babel-plugin-react-compiler`, oggi alla versione `1.0.0`, da
agganciare a `@vitejs/plugin-react` dentro `vite.config.ts`.

⚠️ **Il criterio di questo passo non lo richiede, e la scaletta non ha un passo che lo
installa: è una lacuna del piano.** La decisione è tua, e il cartello `TODO(0.6/7)` in
`vite.config.ts` te la mette davanti. Le due strade sensate:

- **attivarlo qui**, allargando di poco il passo — il codice da ottimizzare oggi è quasi nullo,
  quindi è il momento più economico per farlo;
- **aggiungere un passo `0.6b`** dedicato, e tenere questo sulla sola migrazione.

Finché non è attivo, il divieto di `useMemo` nel `CLAUDE.md` sta chiedendo una cosa senza
fornire il sostituto.

## 7. `react` e `@types/react` sono due pacchetti diversi
---

Questo punto genera più confusione di tutti gli altri messi insieme, quindi vale la pena
essere espliciti.

- **`react`** è il codice che gira davvero nel browser. Lo pubblica il team di React.
- **`@types/react`** non contiene nemmeno una riga eseguibile: è solo la **descrizione dei
  tipi**, che serve a `tsc` e all'editor. Lo pubblica un progetto della community,
  *DefinitelyTyped*, con tempi e numeri di versione propri.

Al momento in cui scrivo sono entrambi alla `19.3.0`, ma la coincidenza è casuale: in altri
periodi i due numeri divergono.

**L'errore tipico** è aggiornare `react` e `react-dom` lasciando i tipi alla 18. Il risultato è
che l'applicazione **gira benissimo nel browser** mentre `tsc` sputa errori incomprensibili su
`ReactNode` e sulle firme dei componenti: il motore è nuovo, il libretto di istruzioni è
vecchio.

> Sono quattro pacchetti da muovere insieme: `react`, `react-dom`, `@types/react`, `@types/react-dom`.

Due cose cambiano nei tipi della 19:

- il namespace globale `JSX` si è spostato dentro React. Dove scrivevi `JSX.Element` ora si
  scrive `React.JSX.Element`;
- `ReactNode` è diventato più stretto: alcune firme che prima passavano ora non passano.

Esiste un codemod ufficiale che fa queste sostituzioni da solo:

```bash
npx types-react-codemod@latest preset-19 ./src
```

Su questo progetto ci sono quattro file di codice in tutto: guardarli a mano è più istruttivo.

## 8. Una sola copia di React
---

Dopo l'installazione, `npm ls react` deve mostrare **una versione sola**, con tutto il resto
marcato `deduped` — che significa «questa libreria voleva React e sta usando quello già
presente».

Se ne comparissero due, l'app si romperebbe con `Invalid hook call`: un messaggio che parla di
hook mentre il problema sta nell'albero delle dipendenze.

**Perché proprio gli hook.** Un hook non è magia: è una funzione che legge e scrive uno stato
tenuto in una variabile **interna al modulo React** che la ospita. `useState` non sa da solo in
quale componente si trova: lo chiede a quella variabile, che React riempie subito prima di
eseguire il corpo del componente. Se il componente è stato montato dalla copia A di React ma
chiama lo `useState` della copia B, in B quella variabile è vuota, e React conclude l'unica
cosa che può concludere: «questo hook è stato chiamato fuori da un componente».

Buona notizia, verificata sulle librerie già installate: dichiarano tutte di accettare React
19, quindi nessuna si porterà dietro una copia propria.

```
@mui/material@7.3.4    -> react: ^17.0.0 || ^18.0.0 || ^19.0.0
react-router@7.9.5     -> react: >=18
react-redux@9.2.0      -> react: ^18.0 || ^19
@emotion/react@11.14.0 -> react: >=16.8.0
```

## 9. Cosa fare, in ordine
---

1. In `package.json`, porta a `^19.0.0` **quattro** pacchetti: `react` e `react-dom` fra le

5. `npm run dev` — apri il browser e **guarda la console**: il criterio chiede che sia pulita.
6. Decidi sul React Compiler (sezione 6) e cancella il cartello `TODO(0.6/7)` con la scelta
   fatta, qualunque essa sia.

- aggiungere i flag stretti al `tsconfig` → passo **0.7**
