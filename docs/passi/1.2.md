## 1. Il problema

### 1.1 Prima del CORS: la same-origin policy

Per capire il CORS bisogna partire dalla regola che il CORS **allenta**.

Un'**origine** è la terna **schema + host + porta**: `http://localhost:5173` è un'origine, e
`http://localhost:8000` è un'**altra** origine, perché cambia la porta. Il percorso non ne fa
parte: `http://localhost:5173/login` e `http://localhost:5173/app` hanno la stessa origine.

La **same-origin policy** è una regola del **browser**: il JavaScript di una pagina può
**leggere** le risposte solo dalla propria origine. Esiste per via dei cookie. Il browser
allega i cookie di un sito a **ogni** richiesta verso quel sito, chiunque l'abbia avviata. Se
la regola non ci fosse, una pagina qualsiasi aperta in un'altra scheda potrebbe fare
`fetch("https://tuabanca.it/api/conto")`, e il browser manderebbe i **tuoi** cookie e
consegnerebbe la risposta a quella pagina.

> La same-origin policy non protegge il server: protegge i dati dell'utente dalle pagine
> degli altri.

### 1.2 Il CORS è l'eccezione controllata

**CORS** — *Cross-Origin Resource Sharing* — è il modo in cui un server dice al browser:
«queste origini, oltre alla mia, possono leggere le mie risposte». Lo dice con degli header
nella risposta, che cominciano tutti con `Access-Control-`.

In Chiaro serve perché, in sviluppo, il frontend gira su `http://localhost:5173` (Vite) e il
backend su `http://localhost:8000`. Sono due origini diverse: senza CORS, il browser
bloccherebbe ogni risposta dell'API al frontend.

### 1.3 Cosa succede in produzione se lo si sbaglia

Il CORS è uno dei punti in cui un errore di configurazione **apre** l'applicazione senza che
niente smetta di funzionare. La configurazione sbagliata più diffusa è questa:

```python
allow_origins=["*"], allow_credentials=True
```

Sembra voler dire «chiunque, con i cookie». Il browser una combinazione del genere non la
accetta, e allora Starlette la «aggiusta» da sé: **rimanda indietro l'origine di chi chiede,
qualunque sia**. L'ho verificato su questo progetto, con un sito estraneo inventato:

```
GET /dati   Origin: https://sito-cattivo.example
200 {"segreto":"dati dell'utente"}
access-control-allow-origin: https://sito-cattivo.example
access-control-allow-credentials: true
```

Vuol dire che qualunque sito può leggere i dati di un utente loggato, usando la sessione di
quell'utente. È una delle vulnerabilità più segnalate nei programmi di bug bounty; la ricerca
che l'ha resa nota è quella di James Kettle,
[Exploiting CORS misconfigurations for Bitcoins and bounties](https://portswigger.net/research/exploiting-cors-misconfigurations-for-bitcoins-and-bounties).

Il secondo errore è meno grave ma più frequente: un'origine scritta male nella configurazione
— con la barra finale, per esempio — **non combacia mai**, e il frontend riceve errori CORS
senza che il server segnali niente. Lo vedi nella sezione 3.

## 2. Il meccanismo

### 2.1 Richieste semplici e preflight

Il browser divide le richieste verso un'altra origine in due famiglie.

**Le richieste semplici** — un `GET`, oppure un `POST` di un form — partono **subito**. Il
browser le manda, il server le esegue e risponde, e solo **dopo** il browser guarda gli
header CORS della risposta: se l'origine della pagina non è autorizzata, **nasconde la
risposta** al JavaScript.

**Tutte le altre** — un `POST` con corpo JSON, un `PATCH`, un `DELETE`, una richiesta con un
header personalizzato — sono precedute da un **preflight**: una richiesta `OPTIONS` che chiede
il permesso prima di mandare quella vera.

```
OPTIONS /api/analisi
Origin: http://localhost:5173
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type
```

Se il server risponde di sì, il browser manda la richiesta vera. Se risponde di no, la
richiesta vera **non parte**. Il frontend di Chiaro parla con l'API in JSON, quindi quasi
tutte le sue chiamate passano dal preflight.

### 2.2 Gli header della risposta

| **_Header_** | **_Cosa dice_** |
| --- | --- |
| `Access-Control-Allow-Origin` | quale origine può leggere la risposta. Una sola, oppure `*` |
| `Access-Control-Allow-Credentials` | se la richiesta può portare i cookie, e la risposta essere letta lo stesso |
| `Access-Control-Allow-Methods` | nel preflight: quali metodi sono ammessi |
| `Access-Control-Allow-Headers` | nel preflight: quali header di richiesta sono ammessi |
| `Access-Control-Max-Age` | per quanti secondi il browser può ricordare l'esito del preflight |

### 2.3 ❗ Le credenziali cambiano le regole

Senza credenziali, `Access-Control-Allow-Origin: *` è legittimo: vuol dire «dati pubblici,
leggibili da chiunque». **Con** le credenziali — cioè quando la richiesta porta i cookie — il
browser applica regole più severe, scritte nella specifica Fetch:

- l'origine deve essere **quella esatta**: con `*` il browser blocca la risposta;
- anche `*` nei metodi e negli header perde il significato di «tutti», e viene letto alla
  lettera.

La ragione è quella della sezione 1.1: una risposta letta *con i cookie dell'utente* contiene
i suoi dati, e il server deve nominare esplicitamente chi può vederli.

Chiaro userà una sessione con cookie dalla fase 2. Il frontend, al passo 3.5, chiamerà l'API
con `credentials: 'include'`, e senza `Access-Control-Allow-Credentials: true` il cookie non
viaggerebbe. È per questo che in questo progetto `*` **non può comparire fra le origini**,
nemmeno per comodità.

> Con i cookie, un server CORS deve dire chi, per nome. `*` vuol dire «non lo so».

### 2.4 ⚠️ Il CORS lo applica il browser, non il server

È la cosa più importante del passo, e la più fraintesa. Guarda cosa succede con una richiesta
semplice da un'origine **non** autorizzata, sulla configurazione di oggi:

```
GET /dati   Origin: https://sito-cattivo.example
200 {"segreto":"dati dell'utente"}
access-control-allow-credentials: true
```

Il server ha **eseguito** la richiesta e ha **mandato** la risposta. Manca solo
`Access-Control-Allow-Origin`, e quella mancanza è un'istruzione per il browser: «non darla a
quella pagina». Ne seguono tre cose:

- 👉 `curl`, Postman o uno script **ignorano** il CORS: per loro gli header sono solo testo;
- 👉 il CORS **non protegge il server** da chi lo chiama direttamente. Lo protegge
  l'autenticazione, che arriva nella fase 2;
- 👉 il CORS **non ferma le richieste**, ferma la **lettura** delle risposte. Una richiesta
  semplice che modifica dati arriva comunque a destinazione: è il problema del CSRF, e si
  risolve al passo 2.8.

Il preflight, invece, il server lo **rifiuta** davvero: risponde `400`, e il browser non manda
la richiesta vera. È il comportamento che il criterio ti chiede di verificare con `curl`.

### 2.5 Chi fa cosa in questo progetto

Gli header li scrive il **`CORSMiddleware`** di Starlette, a cui FastAPI fa da tramite. È un
middleware, quindi agisce su **tutte** le risposte, comprese quelle di errore: è la ragione per
cui in `main.py` viene registrato per ultimo, ed è il più esterno della pila. Quel commento in
`main.py` resta valido.

Il passo divide il lavoro in due funzioni, in un modulo nuovo, `app/core/cors.py`:

- **`leggi_origini(valore)`** trasforma il testo di `BACKEND_CORS_ORIGIN` in un elenco di
  origini, e **rifiuta** quelle scritte male. È chiamata dal validatore dei settings, così
  un'origine sbagliata ferma l'avvio con il messaggio che hai scritto al passo 1.1;
- **`aggiungi_cors(app, origini)`** registra il middleware con la politica che decidi tu.

Separarle dai settings e da `main.py` le rende **testabili da sole**: i test costruiscono
un'app di prova e ci chiamano sopra `aggiungi_cors()`, senza dipendere dall'ambiente.

## 3. Gli errori tipici

**`*` con le credenziali.** Vedi 1.3. Starlette non lo rifiuta: rimanda l'origine di chiunque.
È il motivo per cui `leggi_origini()` deve rifiutarlo **prima** che arrivi al middleware.

**La barra finale.** `http://localhost:5173/` non è un'origine: è un URL con un percorso. Il
browser nell'header `Origin` la barra non la mette mai, e il confronto è fra stringhe esatte.
Verificato:

```
allow_origins=["http://localhost:5173/"]
GET da http://localhost:5173        → nessun access-control-allow-origin
preflight da http://localhost:5173  → 400 Disallowed CORS origin
```

Nessun avviso all'avvio: il frontend semplicemente smette di funzionare.

**Schema o porta diversi.** `http://` e `https://` sono origini diverse, e lo sono anche
`http://localhost` e `http://localhost:5173`. Lo stesso vale per `localhost` contro
`127.0.0.1`: per il browser sono due host diversi.

**Maiuscole.** Il browser scrive l'origine in minuscolo. `HTTP://LOCALHOST:5173` nella
configurazione non combacerebbe mai: è una delle decisioni della mossa 1.

**`allow_headers=["*"]`.** Starlette lo traduce in «qualsiasi header mi chiedano»: il preflight
con un header inventato passa. Verificato:

```
Access-Control-Request-Headers: x-qualsiasi
200 OK   access-control-allow-headers: x-qualsiasi
```

Un elenco esplicito, invece, lo rifiuta con `400 Disallowed CORS headers`.

**Credere che il CORS fermi la richiesta.** Vedi 2.4. Chi lo crede finisce per affidare al
CORS un compito di sicurezza che non ha.

**`curl` in PowerShell.** In Windows PowerShell 5.1, `curl` è un alias di `Invoke-WebRequest`,
che ha altri parametri. Per le prove del criterio scrivi **`curl.exe`**.

## 4. Riferimento della sintassi

### 4.1 Smontare un URL: `urlsplit`

```python
from urllib.parse import urlsplit

pezzi = urlsplit("https://esempio.it:8443/app?x=1#a")
pezzi.scheme     # 'https'
pezzi.netloc     # 'esempio.it:8443'    host e porta insieme
pezzi.path       # '/app'
pezzi.query      # 'x=1'
pezzi.fragment   # 'a'
```

Come si comporta sui casi che ti interessano, verificato:

```
'http://localhost:5173'    scheme='http'       netloc='localhost:5173'  path=''
'http://localhost:5173/'   scheme='http'       netloc='localhost:5173'  path='/'
'localhost:5173'           scheme='localhost'  netloc=''                path='5173'
'*'                        scheme=''           netloc=''                path='*'
'HTTP://LOCALHOST:5173'    scheme='http'       netloc='LOCALHOST:5173'  path=''
```

Nota l'ultima riga: `urlsplit` porta lo schema in minuscolo, ma l'host lo lascia com'è.

### 4.2 Un validatore di campo in pydantic

```python
from pydantic import BaseModel, field_validator

class Ordine(BaseModel):
    codice: str

    @field_validator("codice")
    @classmethod
    def controlla_codice(cls, valore: str) -> str:
        if not valore.startswith("ORD-"):
            raise ValueError(f"il codice {valore!r} deve cominciare con ORD-")
        return valore
```

- il validatore riceve il valore **già convertito** nel tipo del campo, e restituisce quello
  da salvare;
- un `ValueError` sollevato lì dentro pydantic lo trasforma in un `ValidationError`, con il
  messaggio preceduto da `Value error, `. In Chiaro arriva quindi da solo al messaggio di
  `carica_settings()`;
- `@classmethod` va **sotto** `@field_validator`, non sopra.

### 4.3 Il middleware

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=[...],        # elenco di origini esatte
    allow_credentials=...,      # True / False
    allow_methods=[...],        # elenco di metodi: "GET", "POST", ...
    allow_headers=[...],        # elenco di header di richiesta ammessi
    max_age=600,                # facoltativo: secondi di cache del preflight (600 è il default)
)
```

Esempio su un altro caso, un'API pubblica di sola lettura, senza cookie:

```python
app.add_middleware(CORSMiddleware, allow_origins=["*"], allow_methods=["GET"])
```

Lì `*` va bene, proprio perché le credenziali non ci sono.

### 4.4 Le prove con `curl`

```bash
curl.exe -i -X OPTIONS http://127.0.0.1:8000/docs -H "Origin: http://esempio.test" -H "Access-Control-Request-Method: POST"
```

- `-i` mostra anche gli header della risposta, che sono la cosa da guardare;
- `-X OPTIONS` sceglie il metodo: senza, `curl` fa un `GET`;
- `-H "Nome: valore"` aggiunge un header. Con `Origin` e `Access-Control-Request-Method`
  insieme, `curl` imita il preflight di un browser.

Poi la prova a mano. Nel tuo `.env` c'è già `BACKEND_CORS_ORIGIN=http://localhost:5173`:
avvia `pipenv run dev` e, in un altro terminale:

```bash
# 1. preflight da un'origine non in elenco → 400 Disallowed CORS origin
curl.exe -i -X OPTIONS http://127.0.0.1:8000/docs -H "Origin: https://sito-cattivo.example" -H "Access-Control-Request-Method: POST"

# 2. preflight dall'origine del frontend → 200, con access-control-allow-origin
curl.exe -i -X OPTIONS http://127.0.0.1:8000/docs -H "Origin: http://localhost:5173" -H "Access-Control-Request-Method: POST"

# 3. richiesta semplice da un'origine non in elenco → 200, ma SENZA access-control-allow-origin
curl.exe -i http://127.0.0.1:8000/docs -H "Origin: https://sito-cattivo.example"
```

La terza è quella da guardare due volte: la risposta arriva, e capire perché è il passo.

Infine, `BACKEND_CORS_ORIGIN=*` nel `.env`: l'app non deve partire, e il messaggio deve dire
perché.
