# 0.3 — Correzione del bug `get_project_root()`

> **Nota sulla provenienza.** Questo passo è marcato 🔴, quindi l'implementazione
> spetterebbe all'autore. È stata scritta da Claude su autorizzazione esplicita e
> circoscritta a questo solo passo, con l'istruzione di non annotarla in
> `DEBITO-DI-APPRENDIMENTO.md`. Il briefing resta comunque scritto per intero: serve
> a poter ricostruire il ragionamento in un secondo momento, ed è la parte che
> l'esecuzione automatica non sostituisce.

## 1. Il problema

`app/core/config.py` calcolava la radice del progetto contando i livelli di cartella
a partire dalla posizione del file:

```python
def get_project_root() -> Path:
    """
    Ritorna la radice del progetto.
    Se questo file è in app/core/config.py -> parents[2] è la repo root.
    """
    return Path(__file__).resolve().parents[2]

DOTENV = (get_project_root() / ".env")
```

Ci sono due difetti distinti, e conviene tenerli separati perché hanno gravità
diversa.

**Il primo è che il nome e la docstring mentono.** Il file sta in
`backend/app/core/config.py`, quindi `parents[2]` è `backend/`, non la radice della
repository, che è `chiaro/`. La misura effettiva:

```
parents[0] = .../chiaro/backend/app/core
parents[1] = .../chiaro/backend/app
parents[2] = .../chiaro/backend      <- quello che il codice usava
parents[3] = .../chiaro              <- la vera radice della repo
```

Questo difetto, da solo, non rompe niente: `.env.example` sta in `backend/`, quindi
il `.env` va cercato proprio lì e il valore restituito è quello giusto. È un bug
**latente**, e i bug latenti sono i peggiori da lasciare in giro, perché il primo
che legge la docstring si fida.

**Il secondo è che il conteggio lega il percorso alla posizione esatta del modulo.**
Annidare `config.py` di una sola cartella — cosa che succede appena la
configurazione cresce e si divide in più file — sposta la radice senza che nulla
protesti. Riprodotto su due alberi identici, uno con `config.py` in `app/core/` e
uno in `app/core/settings/`:

```
CASO a:  DOTENV -> .../backend/.env         esiste: True    PROJECT_NAME: 'Chiaro'
CASO b:  DOTENV -> .../backend/app/.env     esiste: False   PROJECT_NAME: ''
```

## 2. Il meccanismo

`Path.parents` è la sequenza degli antenati di un percorso, dal più vicino al più
lontano. È indicizzata per **posizione**, non per significato: `parents[2]`
significa «due livelli sopra», non «la radice del progetto». Nessuna delle due cose
implica l'altra, e la seconda è ciò che serve.

Il modo robusto di risolvere una radice è **ancorarla a un marcatore**: si risale
l'albero finché non si trova una cartella che contiene un file che per costruzione
può stare solo nella radice. Qui il marcatore è il `Pipfile`, che dichiara le
dipendenze del progetto Python e quindi non può trovarsi altrove.

```python
MARCATORE_RADICE = "Pipfile"

def risali_fino_al_marcatore(partenza: Path, marcatore: str = MARCATORE_RADICE) -> Path:
    for candidato in (partenza, *partenza.parents):
        if (candidato / marcatore).is_file():
            return candidato
    raise RuntimeError(...)
```

La profondità di partenza diventa irrilevante, ed è esattamente la proprietà che
mancava.

## 3. Gli errori tipici

**Fidarsi del fatto che «funziona».** Il codice originale restituiva il percorso
giusto per coincidenza. Un test che si limita a verificare il valore corrente
sarebbe passato anche prima della correzione, quindi non avrebbe protetto da
niente: il test utile è quello che varia la profondità del modulo.

**Non sapere che `pydantic-settings` ignora in silenzio un `env_file` inesistente.**
È la ragione per cui questo bug è pericoloso in produzione. Non c'è eccezione, non
c'è warning: i campi prendono i valori di default e l'applicazione parte. Con
`PROJECT_NAME` vuoto si nota poco; con `BACKEND_CORS_ORIGIN` vuoto il frontend
smette di poter chiamare l'API e la causa è invisibile nei log.

**Usare `os.getcwd()` invece di `__file__`.** Sposta il problema: il percorso
diventa dipendente dalla cartella da cui si lancia il processo, che cambia tra
sviluppo, test e container.

**Non far fallire il caso «marcatore assente».** Se la funzione restituisse un
valore di comodo invece di sollevare un'eccezione, il fallimento tornerebbe
silenzioso e si sarebbe girato in tondo.

## 4. La soluzione adottata

- `MARCATORE_RADICE = "Pipfile"`, costante esplicita invece di un numero.
- `risali_fino_al_marcatore(partenza, marcatore)`, che accetta il punto di partenza
  come parametro: è ciò che la rende testabile su alberi finti, senza spostare file
  veri.
- `get_backend_root()`, che sostituisce `get_project_root()`. **Il nome è cambiato di
  proposito**: la funzione ritorna la radice del *backend*, non quella della
  repository, e il nome vecchio era metà del bug.
- `DOTENV = get_backend_root() / ".env"`, invariato nel comportamento e ora
  invariante rispetto alla posizione del modulo.

```bash
cd backend && pytest tests/ -v
```

Cinque test, tutti verdi:

| Test | Cosa dimostra |

| `test_la_radice_contiene_il_marcatore` | la radice è la cartella con il `Pipfile` |
